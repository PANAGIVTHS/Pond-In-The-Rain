GPGPU: a SIMT processor on an FPGA

A general-purpose GPU core that we designed from an empty repository: a streaming multiprocessor of 32 RISC-V lanes executing in lockstep, a memory subsystem that coalesces the lanes' accesses into AXI4 bursts to DDR, and a host interface with control registers, interrupts, fault reports and performance counters. It runs on a Zynq-7020 next to the ARM cores. The ARM loads a compiled C kernel, starts it, and the kernel writes its frames into a framebuffer that the board scans out over HDMI at 720p.

SystemVerilogRISC-V RV32I + MULSIMTAXI4 / AXI4-LiteVerilatorVivado / VitisZynq-7020Python
32lanes per SM, set by one parameter
5stage pipeline, shared fetch/decode
720pHDMI output from DDR framebuffers
45directed RTL tests + random programs

The system

The GPU is a custom AXI IP in the FPGA fabric. The ARM processor sees it as a block of control registers on an AXI4-Lite port: it writes the kernel into instruction memory, sets CONTROL.START and waits for the completion interrupt. The GPU reaches the board's DDR through its own AXI4 master on a high-performance port, where two framebuffers and a general data region live. A VDMA reads the front framebuffer and streams it to an HDMI encoder.

Inside the streaming multiprocessor

The multiprocessor follows the SIMT model: one instruction stream drives every lane. Fetch and decode are shared, so the 32 lanes cost one instruction memory and one decoder. Each lane (a streaming processor) has its own register file, ALU, three-stage DSP multiplier and forwarding network, and carries the instruction through execute, memory and write-back. Register x31 starts at the lane's index, which is how a kernel tells its threads apart. A hazard unit tracks dependencies for the warp as a whole, because all lanes are at the same instruction.

Memory: turning 32 accesses into a few bursts

Every lane can issue a load or store in the same cycle, so the memory subsystem is where most of the design effort went. A port controller decodes each lane's address against the memory map and its permissions: local data memory in BRAM, the two framebuffers, or general memory in DDR. BRAM requests are served by an arbiter that picks the lowest-numbered lanes each cycle. DDR requests go through a group former that coalesces lanes touching the same burst into one group. Groups enter a write ring or a read ring, whose slots track bursts in flight in AXI order, so several bursts can be outstanding while the R and B responses come back. A lane that touches an unmapped or forbidden address, or gets an AXI error, raises a fault that records the faulting PC and lanes for the host.

Running real programs

Kernels are ordinary C compiled with GCC for rv32im. A small runtime gives each lane its own stack and its thread index, and a kernel ends with ecall: the warp stops issuing, lets older instructions drain, then raises the completion interrupt. Programs written for it include a Mandelbrot zoom, Julia sets, 2D and 3D N-body, metaballs, a ripple effect, a terrain renderer, a rotating cube, a triangle rasteriser and a Sobel filter, plus stress and fault-injection kernels.

Verification

  • a Python model of the GPU produces the expected registers, data memory and DDR contents for every test program
  • 45 directed test programs, plus a random program generator with reproducible seeds, run on the RTL in Verilator
  • three benches: the multiprocessor alone, end-to-end through the AXI4-Lite interface and IRQ, and the DDR path against an AXI4 slave model that injects latency, back-pressure and SLVERR/DECERR errors
  • a gpgpu command-line tool that drives Vivado, Vitis, Verilator, GCC and the board (build caching, waveforms, board upload) from one YAML configuration

What was hard

Getting the pipeline right before scaling it. We started with a three-stage core, moved to five stages, added forwarding and a hazard unit, and only then split it into a shared front end and per-lane back ends. Data hazards, stalls and a global memory stall all have to agree across 32 copies of the datapath.

A monitor that went black. Under heavy GPU load the HDMI monitor lost sync, while a capture card showed a perfect picture. We ruled out the video pipeline, measured supply voltages with the XADC, estimated power and swept the GPU clock. The cause was the GPU's switching disturbing the global clock network that fed the HDMI serializers. Moving their clock onto regional clock buffers next to the HDMI pins fixed it, with no RTL change.

My part

I built the first core: the original three- and five-stage pipelines, the hazard unit and forwarding, the split into a streaming multiprocessor and per-lane streaming processors, scaling to any number of lanes, and the pipelined multiplier. I also wrote the first test infrastructure (the assembler, the golden-state generator and the random tester), did the SystemVerilog migration of the core, and designed the experimental warp scheduler, scoreboard and warp masks, each with its own testbench, as groundwork for running several warps.

Faster CV32E40P by removing forwarding

Forwarding saves stall cycles, but on an FPGA its multiplexers and long wires can become the critical path. We took CV32E40P, the OpenHW Group's four-stage in-order RISC-V core, and built three variants that remove selected execute-stage forwarding paths: no multiplier forwarding, no ALU forwarding, and both. Correctness is kept by stalling the dependent instruction until the value arrives through write-back. Each variant was then judged on Vivado post-implementation reports and on cycle counts from real benchmarks, because a faster clock is only a win if the extra stalls don't eat it.

SystemVerilogRISC-V RV32IMVivadoZedBoardIcarus / sv2vPython
73.2 MHzno-MUL-forwarding variant, from 66.8 MHz
≈ −9%execution time on benchmarks with no MUL dependencies
9.9%break-even MUL dependency rate
+3%LUTs, same DSPs, BRAM and power

Method

  • each variant lives in its own CV32E40P submodule and goes through the same flow
  • RTL regressions: assembly tests (including dependency stress cases) run in simulation and compared against a Python golden model
  • benchmarks: bare-metal RV32IM C programs (vvadd, median, sort, rsort, multiply, matrix multiply, Dhrystone, SHA-256, an IoT-style FSM, IPv4 packet processing) with region-of-interest cycle counts
  • Vivado: the same minimal ZedBoard wrapper (core + BRAM IMEM/DMEM) for every variant, scripted post-implementation timing, utilisation and power reports

Results

variantperiodWNSest. FmaxLUTs
baseline15 ns0.030 ns66.8 MHz4171
no MUL fwd14 ns0.339 ns73.2 MHz4314
no ALU fwd15 ns0.114 ns67.2 MHz4200
no ALU + MUL fwd15 ns0.630 ns69.6 MHz4186

The baseline's critical path ran from the decode-stage operand registers into the register file, and 12.8 ns of its 14.9 ns was routing. A histogram of the 1000 slowest paths showed the reason: the baseline's delays were smeared all the way up to 14.9 ns, a sign of routing congestion around the operand multiplexers. Removing forwarding sources pulled that tail back below 14.2 ns.

A simple model tells when the trade pays off: with CPI 1 and one stall per dependent multiply, the faster clock wins while fewer than 9.9% of instructions consume a multiply result immediately. The benchmarks agreed: programs with no such dependencies ran about 9% faster, multiply (7.7%) gained 2%, and matrix multiplication (10.4%) lost 0.4%.

CUDA N-body: 2910× faster

The final project of a high-performance computing course: a simulator of many independent galaxy-like particle systems, where every body pulls on every other. Starting from a sequential C version, we built an OpenMP version and then a ladder of CUDA versions, each one checked against the CPU output and measured over 25 runs on a server with Tesla K80 GPUs.

What we learned

Occupancy isn't everything. Asking __launch_bounds__ for four blocks per SM capped the kernel at 64 registers and caused heavy register spilling; allowing two blocks per SM gave it 128 registers, no spills, and about twice the throughput. The compiler's -Xptxas -v output showed exactly why.

Not every textbook trick helps. Thread coarsening on its own made the kernel slower (72 vs 85 billion interactions/s), because of the extra register pressure.

The rest of the course

  • Sobel on one CPU core: loop interchange, unrolling, fusion, strength reduction and faster maths gave up to 21× with the Intel compiler
  • OpenMP K-means: parallel loops with critical sections, atomics and SIMD reductions, compared by timing
  • CUDA 2D convolution: block sizing, padding to remove divergence, float vs double precision and memory-to-FLOP ratios
  • CUDA CLAHE: privatised histograms, an inclusive parallel scan, coalesced access, streams and events; 1.9× over our first GPU version and about 24× over the CPU

Leaking data through DDR emissions

Air-gapped computers have no network, so they are assumed to keep their secrets. But every fast-switching bus radiates, and DDR memory switches very fast. We built a complete covert channel: an unprivileged program on the target encodes data in the pattern of its memory traffic, and a software-defined radio nearby turns the resulting electromagnetic noise back into bits.

CSSE2 non-temporal storesADALM-PLUTO SDRGNU RadioOOKPython
2 mlongest successful transfer
128 bit/shighest bitrate decoded
0privileges or hardware changes on the target

How it works

  • Transmitter: a user-space C program sends each bit as a time slot. For a 1 it hammers memory, for a 0 it stays idle. It uses non-temporal (cache-bypassing) stores so the traffic really reaches the DDR bus instead of staying in the CPU caches.
  • Framing: a preamble (10101001) for alignment and an end-of-message marker, so the receiver can find a payload such as a 128-bit AES key.
  • Receiver: an ADALM-PLUTO SDR tuned to the memory bus emissions, with a GNU Radio flowgraph that filters the band and demodulates the on-off keying into a bitstream.
  • Recovery: Python tools align on the preamble, decode the message and count bit errors against the original.

Results

We logged runs at 25, 50 and 100 cm across bitrates from 2 to 128 bit/s, with bit-error counts for each, including perfect transfers of the AES key. The longest successful transfer was at 2 metres, at 128 bit/s.

FPGA · HIGH-LEVEL SYNTHESIS · TEAM OF 2 · 2025 · ECE340 EMBEDDED SYSTEMS

Smith-Waterman on an FPGA

Smith-Waterman finds the best-matching region between two DNA or protein sequences by filling a scoring matrix where every cell depends on its left, upper and upper-left neighbours. We optimised it in software on x86 and on the Zynq's ARM core first, then redesigned it as a hardware kernel with Vitis HLS and OpenCL/XRT.

CVitis HLSOpenCL / XRTZynq ARMperfIntel Advisor

Software first

Six software versions on x86 reached 3.81× on the largest input: branch-free maximums that compile to cmov (95× fewer branch misses), reusing each cell's neighbours in registers instead of reloading them, and padding to drop edge checks. A roofline model from Intel Advisor showed each version moving away from the memory-bandwidth limit. On the ARM core the same code behaved differently: there is no cmov, and the cache-unfriendly anti-diagonal version was slower than the original.

Then hardware

The cells on one anti-diagonal don't depend on each other, so the kernel walks the matrix diagonal by diagonal and computes a whole diagonal in parallel. Seven implementations, each analysed in Vitis, got there step by step:

  • keep only the three live diagonals in a circular buffer instead of the whole matrix
  • cyclic array partitioning (factor 16) for parallel BRAM access, then BIND_STORAGE to move arrays from LUTs into BRAM
  • exact bit-widths for every variable, which cut LUT, flip-flop and BRAM use
  • the maximum search moved out of the main loops, and a shift-register sliding window over the database string
  • breaking the loop-carried dependency between the max tracking and the diagonal pointer, the last thing between II = 2 and II = 1

What didn't work

Every implementation passed software and hardware emulation, but most failed when deployed on the board. We traced the problem to the kernel code itself, not the host program or the tools, but ran out of time before finding it. One variant did run on the FPGA: Vitis estimated 1.6 ms for a 32 × 65536 input, and the board measured 8.8 ms.

This Pond

The background of this site is a small, living koi pond drawn entirely out of text characters. Koi swim, rain falls, lanterns drift and autumn leaves fall, and the pond reacts to you and to the page on top of it. There are no images, sprites, libraries or sound files: everything is computed in about 660 lines of plain JavaScript and painted onto one canvas, sixty times a second.

JavaScriptCanvas 2DWeb Audiono libraries~660 lines60 fps

How it's drawn

The screen is treated as a grid of character cells, like a terminal. Every frame the pond is built into a few layers, one value per cell: the water's light, ripple rings, lantern glow, the koi, the leaves and the title. Then each cell gets one character and one colour. Shapes are never stored as pictures; they're described by maths and "sampled" into cells, so the whole scene can move and resize freely.

  pond state            per-cell layers            one canvas
  koi, ripples,   ──►   glyph + colour      ──►   one character
  light, leaves         for every cell            per cell

The shimmering light on the water comes from two slowly drifting noise fields: where their values meet, light gathers into a moving net of · - ~. Ripples are rings drawn with whichever of - \ | / follows the ring's curve at that point, which is why they look round even though they're made of text.

The koi

Each koi is a chain of eleven points: the head swims, and the body follows the path the head took, so it bends naturally through turns. For every cell near a koi, the code finds the closest point on that spine, works out how far across the body the cell is, and shades it as if lit from the upper left, choosing a denser character for shadow and a lighter one for light (@%#&8o*+:). Nine real koi varieties (kohaku, tancho, showa, asagi and others) are just colour rules over the body, and eyes, a forked tail and pectoral fins are added on top.

Their behaviour is a few simple rules working together:

  • each koi has its own home patch and meanders around it, mostly forward, so the pond fills evenly
  • a koi can't turn tighter than its body can follow, so it never folds into itself
  • they keep their distance from each other's bodies, and now and then two swim side by side for a while
  • they flee from clicks, race for food, look at a lantern you light up, and keep out from under the name at the top
  • a koi will occasionally nudge a lantern that drifted behind the page back out to the side

Weather, leaves and sound

Rain drops make small ripples and streaks; lightning flickers the whole scene and the card borders, followed by thunder a moment later. It's always autumn: long olive leaves land, drift to the sides, then darken and sink. All the sound is synthesised live in the browser: rain is filtered pink noise, the drips and the lantern bell are tuned oscillators, and thunder is a burst of noise shaped into a crack and a long roll.

The pond and the page

The pond isn't just behind the page; the two talk to each other. Scrolling drifts the pond and stirs the water; each section has its own light and rain; a koi swimming under a card tints its border in that koi's colour; lanterns warm the cards they float near, raindrops slide down the glass, and the lanterns double as a map of the site.

What was hard

Making koi move like fish. Early versions folded into themselves, slid sideways in rigid U-shapes, or circled forever around a point they could never reach. Each fix came from finding the real cause rather than adding another rule: letting the body follow the head's path, and limiting how tightly a koi can turn based on its own length.

Stopping them from piling up. Watching wasn't enough to tell whether a change helped, so I built a test that fast-forwards fifteen minutes of pond time and counts overlaps and clumps. It showed that clever avoidance rules barely mattered; what mattered was how much open water there is, where the koi start, and keeping their home patches out from under the title.

A readable name made of text. Thin, elegant letters fall apart when they're turned into character cells. The name is now pre-rendered once and sampled into a classic ASCII density ramp, so it looks the same on every device.
